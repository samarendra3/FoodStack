## 3. Indexes

### 3.1 What is already right

The operational tables are indexed around the tenant → branch → time access path:

- `orders`: `(tenant_id, branch_id, created_at DESC)`, the same plus `status` or `channel`, a unique `(tenant_id, branch_id, order_number)`, a partial kitchen index on open tickets, a partial unique `client_request_id` for idempotency, and `(tenant_id, customer_id)`.
- `payments`: `(tenant_id, branch_id, created_at)`, `(…, method, created_at DESC)`, `(tenant_id, order_id)`.
- `inventory_movements`: `(tenant_id, branch_id, created_at DESC)` and `(tenant_id, item_id, branch_id, created_at DESC)`. `inventory_stock` has PK `(tenant_id, branch_id, item_id)`.
- Menu: partial `WHERE deleted_at IS NULL` indexes on `(tenant_id, restaurant_id, sort_order)`, `lower(name)` and category.
- Billing: partial unique "one pending invoice per tenant", gateway order/payment uniqueness, and the open-checkout partial index.
- `audit_logs`: BRIN on `created_at` plus `(tenant_id, created_at DESC)`.

### 3.2 Recommended additions (Phase 2), each tied to a query

| Index                                                                         | Serves                                          | Why                                                                                                           |
| ----------------------------------------------------------------------------- | ----------------------------------------------- | ------------------------------------------------------------------------------------------------------------- |
| `orders (tenant_id, created_at) INCLUDE (status) WHERE status <> 'cancelled'` | Monthly order limit (F1)                        | Index-only count of a tenant's month without touching the heap. Later superseded by a counter row.            |
| `customers USING gin (name gin_trgm_ops, phone gin_trgm_ops)`                 | `ILIKE '%term%'` customer and order search (F8) | **Conditional:** add when a tenant passes ~50k customers, after `EXPLAIN` shows a sequential scan dominating. |
| `menu_items USING gin (lower(name) gin_trgm_ops) WHERE deleted_at IS NULL`    | Menu and POS search                             | Same condition as above.                                                                                      |

Rules for the migration (P2):

- **Size.** Use `CREATE INDEX CONCURRENTLY` for tables that can be large in production (`orders`, `order_items`, `payments`, `customers`, `menu_items`).
- **No transaction.** Concurrent index builds cannot run inside a transaction, so those migrations set `transaction = false` and each statement uses `IF NOT EXISTS`.
- **Failed builds.** A failed concurrent build leaves an `INVALID` index; the migration drops it and retries. §9 has the SQL to find invalid indexes.
- **Small tables.** Plain `CREATE INDEX` inside the normal transactional migration is fine for them.

### 3.3 Not recommended

- **Indexes on low-cardinality columns alone** (`status`, `channel`): the planner will not use them. They are already the second or third column of composite indexes, which is correct.
- **Indexes for the 25 unindexed foreign keys** (`*_by` user references, `plan_id`, `addon_package_id`, `(tenant_id, payment_id)` on refunds, `(tenant_id, membership_id)` on sessions, and similar). No query filters on them, and their parents are effectively never deleted, so each index would cost writes for no reads.
- **Dropping indexes now.** The dev usage counters cannot show which indexes are unused in production. Collect `pg_stat_user_indexes` from production for at least one full business cycle (§9) first.
  - Apparent duplicates such as `orders_tenant_id_id_key` next to `orders_pkey` are **required**: composite foreign keys `(tenant_id, id)` reference them.

## 5. Dashboard and reporting

Today the Restaurant Admin dashboard shows only team counts and the trial card, because no sales endpoint exists. The plan for P6:

- **One endpoint, two queries.**
  - The first aggregates all KPI cards for the requested branch(es) and day: today's sales, order counts by status, average order value, over `orders` in `[startOfDay, now)`. It uses `count(*) FILTER (WHERE …)` and `sum(...) FILTER (...)`, served by `(tenant_id, branch_id, created_at)`.
  - The second returns top items over `order_items` joined to those orders, `LIMIT 5`.
  - Low stock comes from `inventory_stock` against thresholds.
  - Revenue chart: `date_trunc` buckets over the same range.
- **Caching.** Redis with a short TTL (30–60 s), key `tenant:{t}:branch:{b|all}:dash:{date}`, invalidated on order completion and payment.
- **Freshness.** The financial totals shown are labelled with their "as of" time, so a cached value is never presented as live money.
- **No materialized views yet.** At the expected per-branch daily volumes, indexed aggregation over one day is cheap. Revisit with **per-day rollup tables** (`daily_branch_sales`) maintained incrementally if monthly or yearly charts exceed the latency budget. They refresh row by row and avoid full `REFRESH MATERIALIZED VIEW` locks.

## 6. Redis caching design (Phase 4)

| Cache                            | Key                                               | TTL     | Invalidate on                                                         |
| -------------------------------- | ------------------------------------------------- | ------- | --------------------------------------------------------------------- |
| POS menu catalogue               | `fs:t:{tenant}:r:{restaurant}:menu:v{n}`          | 10 min  | Any menu write: bump `v{n}` (versioned key, no `KEYS`/`SCAN` deletes) |
| Active promotions per restaurant | `fs:t:{tenant}:r:{restaurant}:promos:v{n}`        | 2 min   | Promotion writes                                                      |
| Dashboard KPIs                   | `fs:t:{tenant}:b:{branch\|all}:dash:{yyyy-mm-dd}` | 30–60 s | Order complete, payment, refund                                       |
| Order-limit usage (banner)       | `fs:t:{tenant}:usage:{yyyy-mm}`                   | 30 s    | Order create/cancel, add-on grant                                     |
| Plan catalogue (public)          | `fs:public:plans:v{n}`                            | 5 min   | Plan writes                                                           |

Rules:

- **Cache-aside.** Every key starts with the **tenant id** from the authenticated context, never from user input.
- **Fail open on Redis errors.** Read from the database and log once per outage, the pattern the rate limiter already uses.
- **Stampede protection.** A short `SET key:lock NX PX` while one request recomputes; others serve the stale value or wait briefly.
- **Never cache authorization decisions or payment state.** Permissions, subscription status and invoice status stay database-read, so revocation is immediate.

> **Phase 4 status:** implemented as described in `docs/PHASE_4_REDIS_REPORT.md`. Versioned keys, fail-open with a circuit breaker, per-instance single-flight instead of `SET NX` locks (sufficient at these payload sizes), and no authorization, entitlement or payment data cached.

## 7. Background jobs and concurrency (Phases 5 and 7)

- **Jobs.** Today nothing is slow enough to need a queue: no PDF, export or email path exists in the API. CSV export is client-side from paged data. When those features are built, they get processors on the existing queues:
  - **Job ids from the business key** (e.g. `invoice-pdf:{invoiceId}`) for deduplication and idempotency.
  - The existing exponential-backoff defaults.
  - Failed-job retention for inspection.
- **Payment application stays in the request or webhook transaction**, where it is idempotent today. It is **not** moved to a queue.
- **Subscription sweep.** It can move to a BullMQ repeatable job for visibility in queue monitoring; the advisory lock already makes multi-instance runs safe. _(Phase 5 decision: kept as the timer.)_
- **Email (Phase 5, done).** Transactional outbox + `notifications` worker; see `docs/PHASE_5_BULLMQ_REPORT.md`.
- **Pool sizing.**
  - Measure p95 concurrent transactions per instance and set `DATABASE_POOL_MAX` accordingly.
  - Keep instances × pool under `max_connections` minus a margin of about 20.
  - PgBouncer in transaction mode is compatible with the per-transaction `set_config` design.

## 8. Multi-tenant isolation review

- **Database level.** Isolation is enforced by RLS on every tenant table (`FORCE` set), with a fail-closed default when the scope is unset.
- **Platform reads.** They use explicit policies such as `app_is_platform()`. The read-only `platform_read` policy on `user_role_assignments` (added in migration `1798000020000`) lets Super Admin lists show owners.
- **Branch scoping.** Spot-checked on `orders.list`, `orders.create`, inventory, payments and reports: each derives allowed branches from the caller's access and filters `branch_id = ANY($n)`.
  - P7 adds a test per data-table endpoint asserting a branch-scoped user cannot read another branch's rows.
- **No cross-tenant reads found.** No query reads across tenants without the platform scope.
- **Requirements for later phases:**
  - Any new cache, job or rollup must carry the tenant id from the authenticated context.
  - Rollup tables must have the same RLS policy as their source tables.

## 9. Benchmark methodology (to be used before and after each phase)

No figures are reported until these runs exist. Results will be labelled **measured** (actual run, with hardware noted) or **estimated** (complexity reasoning only).

1. **Synthetic data.** A seeding script (P7) generates tenants, branches, menus and orders at three scales:
   - **S:** 100k orders.
   - **M:** 1M orders.
   - **L:** 10M orders, where disk allows. On a developer laptop L may not fit, and will be reported as not run.

   Data is skewed realistically: most tenants small, a few large; orders concentrated in business hours; 3–8 lines per order.

2. **SQL level.** For each critical query (F1, F3, F4, F5, F7, dashboard), capture `EXPLAIN (ANALYZE, BUFFERS)` and `pg_stat_statements` mean, stddev and calls, before and after.
3. **HTTP level.** Load-test with [k6](https://k6.io) run from its Docker image (no repository dependency). Scenarios: order creation (POS), order list (page 1, deep page, date filter, search), dashboard, menu, inventory and billing overview. Report average, p95, p99 and requests per second at fixed concurrency (10 / 50 / 200 virtual users), after a warm-up.
4. **Resources.** Database CPU and buffer hits from `pg_stat_database`, `pg_stat_statements` and `docker stats`. API memory from `process.memoryUsage()`. Redis hit/miss from `INFO stats` (`keyspace_hits` / `keyspace_misses`).
5. **Controls.** Same hardware, same data, cold and warm cache runs reported separately, at least three runs with the median reported.

## 10. Complexity of the main changes (expected; to be verified in §9)

Here n is the rows in the relevant tenant or branch scope, m the rows a query actually returns or touches, and L the lines in an order.

| Operation                        | Before                                                                          | After                                                              | Notes                                                                                      |
| -------------------------------- | ------------------------------------------------------------------------------- | ------------------------------------------------------------------ | ------------------------------------------------------------------------------------------ |
| Order-limit check per order (F1) | O(m) heap rows counted, m = the tenant's orders this month, plus 3 extra counts | O(m) index-only entries (step 1); O(1) with a counter row (step 2) | Step 1 reduces I/O from heap pages to index pages. It does not change growth. Step 2 does. |
| Order creation writes (F3)       | L + d round trips (lines + discounts)                                           | 2 round trips                                                      | Server work is still O(L). The win is network latency and lock hold time.                  |
| Order list with date range (F4)  | O(n) orders in visible branches scanned                                         | O(log n + m) per branch via `(tenant, branch, created_at)`         | Plus sorting cost when the requested sort is not `created_at`.                             |
| Deep page k of orders (F5)       | O(k·limit) skipped rows + O(n) `count(*)`                                       | O(log n + limit) per page with keyset; count only on request       | Keyset gives no "jump to page 37"; the UI offers next/previous for those lists.            |
| Request authorization (F2)       | 4 access queries per request (2 duplicated)                                     | 2                                                                  | Constant-factor saving on every request.                                                   |
| Dashboard (P6)                   | built, see Phase 6 report                                                       | O(log n + m_today) aggregate, O(1) on cache hit                    | m_today = orders in the day and branch scope.                                              |

Index storage overhead for §3.2 will be reported from `pg_relation_size` on the M-scale data set. Each B-tree on `orders` is expected to cost roughly 30–45 bytes per row, depending on columns. GIN trigram indexes are typically several times larger than the text they index, which is why they are conditional.
