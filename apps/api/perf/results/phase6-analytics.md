## 1,000,000 orders — not measured

Three attempts did not produce results, so no 1M figures are claimed:

1. The cumulative run overflowed `integer` in the seeding formula past ~271k orders (bench bug, fixed).
2. The next cumulative run reached 1,000,000 seeded orders but hit Jest's 30-minute test timeout before measuring (timeout raised to 4 h).
3. The 1M-only run was stopped by the host because the machine (8 GiB RAM) ran critically low on memory.

The covering `order_items` index comparison runs after the last size, so it was not measured either.

## Notes on the measured results

- The cache-off concurrent runs at 100k returned HTTP 500 for 2 of 400 requests in this run (31 in an earlier run).
  The logged cause is `timeout exceeded when trying to connect`: the API pool (`DATABASE_POOL_MAX=10`,
  5 s acquire timeout) was exhausted by 80 simultaneous uncached dashboard requests. No 500s with the cache on.
- At 100k orders, `thisYear` statements switch to sequential scans of `orders` (the range covers most rows,
  so PostgreSQL correctly prefers a scan). Uncached year views cost 0.2–0.8 s per statement here; this is the
  case the 900 s closed-range TTL and, later, a daily rollup table would address.
- "Rows read by scans" for itemSales is fractional because PostgreSQL reports average rows per loop.
